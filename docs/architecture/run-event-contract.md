# Run Event Contract

## Purpose
This document defines the stable P0 contract for execution events across:
- engine -> backend callback ingestion
- backend persistence
- backend WebSocket / SSE broadcasting
- run detail payloads consumed by the frontend

Related contracts:
- [ForgeGraph Specs](../../SPECS.md)
- [Marketplace Runtime Contract](marketplace-runtime-contract.md)

## 1. Event Surfaces

### 1.1 Engine callback ingestion
The engine posts execution events to:

`POST /api/runs/engine-events`

This is a service-to-service endpoint authenticated with:
- `X-Forgegraph-Timestamp`
- `X-Forgegraph-Signature`

### 1.2 Browser live updates
The frontend receives live updates through:
- WebSocket run channel
- SSE run stream fallback
- polling fallback

### 1.3 Persisted run detail
`GET /api/runs/{run_id}` is the stable read model for:
- current run state
- nested `node_runs`
- derived `agent_events`
- per-node `agent_trace`

## 2. Canonical Broadcast Event Types

These are the stable live transport event names in P0:
- `run.updated`
- `node_run.updated`
- `node_stream.chunk`
- `run.schema_validation`

## 3. Broadcast Envelope

All live broadcast messages use this envelope:

```json
{
  "event_id": "uuid",
  "timestamp": "2026-03-12T12:00:00Z",
  "type": "run.updated",
  "run_id": "run-uuid",
  "...payload": {}
}
```

Common fields:
- `event_id`: unique event identifier generated by the backend broadcast layer
- `timestamp`: ISO-8601 event timestamp
- `type`: stable event type string
- `run_id`: run identifier

## 4. Event Payloads

### 4.1 `run.updated`

```json
{
  "type": "run.updated",
  "run_id": "run-uuid",
  "run": {
    "id": "run-uuid",
    "status": "running",
    "started_at": "2026-03-12T12:00:00Z",
    "ended_at": null,
    "duration_ms": null,
    "output_json": null,
    "error_message": ""
  }
}
```

Used for:
- lifecycle transitions
- final output propagation
- pause/resume state
- terminal failure/cancel state

### 4.2 `node_run.updated`

```json
{
  "type": "node_run.updated",
  "run_id": "run-uuid",
  "node_run": {
    "node_id": "tool_1",
    "node_type": "tool",
    "status": "succeeded",
    "attempt": 1,
    "started_at": "2026-03-12T12:00:01Z",
    "ended_at": "2026-03-12T12:00:02Z",
    "input_json": {},
    "output_json": {},
    "error_json": null
  }
}
```

Stable node statuses:
- `pending`
- `running`
- `waiting`
- `succeeded`
- `failed`
- `skipped`

### 4.3 `node_stream.chunk`

```json
{
  "type": "node_stream.chunk",
  "run_id": "run-uuid",
  "node_stream": {
    "node_id": "agent_1",
    "node_type": "agent",
    "attempt": 1,
    "chunk": "{\"event\":\"agent.step.started\",\"step_index\":0}",
    "chunk_index": 0,
    "agent_event": {
      "event": "agent.step.started",
      "node_id": "agent_1",
      "node_type": "agent",
      "attempt": 1,
      "step_index": 0,
      "chunk_index": 0
    }
  }
}
```

Rules:
- `chunk` is always the raw streamed string
- `agent_event` is optional
- when present, `agent_event` is the normalized structured form of a streamed agent event

### 4.4 `run.schema_validation`

```json
{
  "type": "run.schema_validation",
  "run_id": "run-uuid",
  "payload": {
    "valid": false,
    "errors": []
  }
}
```

This event is reserved for runtime schema validation feedback.

## 5. Engine Callback Event Types

The engine currently emits callback event types such as:
- `run_started`
- `run_completed`
- `run_failed`
- `run_paused`
- `run_resumed`
- `run_canceled`
- `node_started`
- `node_completed`
- `node_failed`
- `node_skipped`
- `node_retrying`
- `node_stream_chunk`
- `run.schema_validation`

These are translated by the backend into persisted run state and stable broadcast events.

## 6. Agent Stream Events

Agent execution currently emits structured events inside `node_stream.chunk`.

Stable P0 agent event names:
- `agent.step.started`
- `agent.step.completed`
- `agent.tool.called`
- `agent.tool.completed`
- `agent.completed`

Important distinction:
- these are persisted as derived `RunEvent` records
- they are exposed in `GET /api/runs/{run_id}` as `agent_events`
- they are folded into `node_runs[].agent_trace`
- they are not yet a separate live transport event type

## 7. Run Detail Contract

`GET /api/runs/{run_id}` returns:
- top-level run fields
- `node_runs`
- `agent_events`
- pause / resume fields for Human Gate

Relevant stable fields:

```json
{
  "id": "run-uuid",
  "status": "paused",
  "paused_node_id": "human_gate_1",
  "pause_payload": {},
  "node_runs": [
    {
      "id": "node-run-uuid",
      "node_id": "agent_1",
      "node_type": "agent",
      "status": "succeeded",
      "attempt": 1,
      "input_json": {},
      "output_json": {},
      "error_json": null,
      "agent_trace": {
        "stop_reason": "final_answer",
        "step_count": 2,
        "tool_call_count": 1,
        "steps": [],
        "events": []
      }
    }
  ],
  "agent_events": []
}
```

## 8. Policy and Safety Semantics

P0 safety behavior must preserve these outcomes:
- policy-denied runtime execution becomes a failed `node_run.updated`
- run history retains the redacted failure payload
- policy-denied failures are audit-logged as `run.policy_denied`

Error message shape should stay consistent with:
- `policy denied: ...`

This applies to:
- cloud-blocked `exec` tools
- blocked HTTP egress
- denied model/provider policy

## 9. Compatibility Rules

P0 compatibility means:
- existing live event type strings must not change
- `run.updated` and `node_run.updated` payload field names must remain backward-compatible
- new agent event names must be additive and documented here
- new transport event types require frontend updates before rollout
